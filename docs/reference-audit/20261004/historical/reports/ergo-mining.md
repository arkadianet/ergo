## Findings

### EM001 — Historical header reads can use a different branch from the applied candidate parent

**P2 · candidate correctness / parent ancestry · SOURCE_CONFIRMED.** Expected contract: candidate consensus inputs must derive from its applied full-block parent, as stated by the prompt and candidate architecture. A held snapshot guarantees a consistent database view, but the database may legitimately have different best-header and applied-full branches.

The Mining live view delegates its historical-height lookup to `StateStore::get_header_id_at_height` at [state_view.rs:97](/home/arkadias/Coding/remote/ergo/ergo-mining/src/state_view.rs:97); the committed view delegates to `CommittedSnapshot::header_id_at_height` at line136. State's live reader and committed accessor read **HEADER_CHAIN_INDEX**, whereas last-applied header windows and the applied parent use **CHAIN_INDEX**. [Snapshot accessor](/home/arkadias/Coding/remote/ergo/ergo-state/src/store/snapshot/mod.rs:215), State reader144–168 and store2429–2430; full owner hashes are retained in the ledger. Header-only best-chain promotion rewrites HEADER_CHAIN_INDEX at [header_store.rs:665](/home/arkadias/Coding/remote/ergo/ergo-state/src/header_store.rs:665) and787–813 without applying full blocks or rewriting the applied-chain ancestry.

`generate_candidate` reads epoch votes through `ViewChainHeaderReader` at candidate271/915–927 and retarget history through `load_epoch_headers` at candidate319/1035–1054. The latter explicitly uses the applied parent itself for the parent-height slot, but uses the best-header index for older slots. Thus a coherent snapshot can combine an old full parent/root/settings/window with newer competing-branch votes or retarget timestamps. Node's already-open mining latch and unchanged full-parent sequence do not prevent this condition; its publish CAS only checks the applied parent, not ancestry of historical data.

Preconditions are a header-only branch promotion that diverges below the applied parent, followed by a candidate needing an affected retarget or voting epoch. Ordinary off-boundary candidates that need no divergent historical height are unaffected. This is a source-confirmed wrong-input selection, not proof that a resulting block has been accepted or that every branch difference changes the result. **No custom fork demonstration, independent Scala candidate comparison, accepted mined block or consensus-split experiment was executed.** Potential rejection/wasted mining work when votes/timestamps change the computed payload is an inference.

Smallest robust fix: give CandidateStateView an explicit applied-ancestry accessor, or resolve historical headers by walking/looking up the chosen parent ancestry within the same held transaction. Preserve the State best-header API for its legitimate callers. Bind both finished-epoch votes and retarget headers to the candidate parent. Acceptance: an existing ordinary fork fixture whose HEADER_CHAIN_INDEX differs from CHAIN_INDEX should verify all queried ancestors, vote tally and retarget input, then run the produced boundary/retarget block through the downstream validator. Also retain live/snapshot/cache equality. Current parity fixtures deliberately use one synthetic indexed branch, away from epoch/recalc boundaries, so both views make the same incorrect selection if this condition were introduced; their equality cannot catch the root cause. Mining owns this finding; State confirms index semantics and Node supplies lifecycle evidence.

### EM002 — Accepted custom fields can exceed the whole extension-section cap

**P2 · configuration / candidate validation · SOURCE_CONFIRMED.** Expected contract: a configured custom extension must not make served work fail the normal structural rules. [validate_custom_extension_fields](/home/arkadias/Coding/remote/ergo/ergo-mining/src/extension_builder.rs:54) checks each value≤64B, reserved key prefixes and duplicate keys. Config and per-build file resolution use it; `build_candidate_extension_fields` appends generated fields and performs a final duplicate sweep at127–139. Neither path checks serialized total size.

The normal full-block validator enforces rule400, **32,768B for the complete extension** at [extension.rs:67](/home/arkadias/Coding/remote/ergo/ergo-validation/src/block/extension.rs:67), counting `32-byte header ID + VLQ(field count) + Σ(2 key bytes + 1 value-length byte + value)`. An operator can configure sufficiently many distinct nonreserved 64B fields while every current guard succeeds. For example the source formula for 500 such fields alone is `32 + 2 + 500×67 = 33,534B`, before interlinks/epoch fields. This is arithmetic over the reviewed source, **not an executed custom oversized candidate**. The key space permits those distinct keys; no count cap closes the path.

Candidate assembly hashes the list and serves WorkMessage without running the full extension structural validator; genesis also collects supplied custom fields directly. Submitted solutions proceed to normal full validation, which is the remaining enforcement point. Operator misconfiguration or file-backed values growing within their individual limits can therefore produce permanently unmineable work until configuration changes; wasted miner work and eventual apply rejection are inferred from the path, not an observed custom failure. No remote unprivileged configuration or accepted invalid block is claimed.

Fix direction: reject impossible configured totals early and check the **final assembled exact serialized size**, including generated interlinks/epoch framing, before publishing work. Reuse the structural validator/shared size calculation to prevent drift; preserve valid custom namespaces, ordering and roots. File-backed values need the final check on every build. Acceptance: existing ordinary extension-limit fixtures should cover below/at/above the limit at nonboundary and epoch boundary, including dynamic file growth, and validate the emitted section downstream. Current tests cover per-field oversize, duplicates, reserved namespaces and one small propagated custom field, not aggregate cap.
