### NODE-001 — P2 startup/progress — SOURCE_CONFIRMED: fresh pruning omits the state history its apply loop still requires

Expected: a supported fresh pruning node must obtain the parent UTXO state before validating retained suffix blocks, or validate all predecessors before pruning. The ordinary executor still selects best_full+1 (ergo-sync/executor/reorg.rs:393–407), so at height0 it attempts block1 whose sections are below the download floor. SectionNotFound waits/re-registers the same gated window (515–530); merely choosing floor951 instead would still lack block950's UTXO state. STATE's activation helper seeds only download/prune metadata, not historical state.

Source proof: existing mode3_lifecycle.rs:28–31,95–128 initializes genesis plus1200 fresh headers, obtains sentinel951 with keep250, and expressly applies no blocks. prune_activation's tests assert queue start, not a validated forward apply. This establishes incompatible initial download/apply contracts; no new node stall demonstration, invalid acceptance, or mainnet consensus divergence is claimed. Trigger is a fresh data directory with positive keep and headers sufficiently ahead; archive-then-prune stores with real parent state differ.

Fix gate fresh pruning until a valid parent state is installed, or perform ordinary genesis-to-tip validation before dropping old sections; align download and apply ownership only after state acquisition. Preserve root checks and independently decide Scala pruning semantics. Regression: fresh supported Mode3 at a pinned header tip, ordinary section delivery, then actual checked full-block progress/root/box queries and reopen; prove both first apply and retention. Add a separate NiPoPoW-only Mode4 parent-state case. Current floor/restart tests cannot close it.

### NODE-002 — P2 lifecycle — SOURCE_CONFIRMED: explicit shutdown does not own wallet writer or rescan completion

Expected: successful explicit shutdown releases database-owning wallet work and prevents further mutations before promised reopen. boot/api_wiring.rs:279–290 discards the wallet writer JoinHandle, even before api_bind=None is handled. wallet_bridge.rs:1150–1342 owns database, secret storage/state, chain reader, submit handle and mempool view while processing/draining commands. commands/admin.rs:292–338 additionally clones database/chain/store into spawn_blocking for rescan, drops its JoinHandle and replies success (meaning admitted background work). Its cancellation predicate is rescan identity ownership (321), not RunHandle shutdown. handle.rs:295–325 drains API and joins indexer/loop but has no wallet/rescan handle or cancellation barrier.

The source proves missing ownership/join; retained DB references and mutations after shutdown are consequences when admitted wallet work is still running, not a newly measured reopen failure. Trigger: supported API/wallet node with an active rescan or queued/in-flight wallet operation during explicit shutdown in a surviving runtime. Genesis/no-work native smoke and mining reopen tests do not exercise this case. A process terminating its runtime differs from the public embedded shutdown contract.

Fix retain writer/rescan ownership in a node-scoped supervisor, close command admission, revoke rescans at safe chunk boundaries, and join all admitted work before reporting shutdown completion. Avoid aborting redb atomic writes. Regression: barrier-held ordinary rescan/wallet command, shutdown with cancellation of the caller too, worker exit/error propagation and immediate same-process DB reopen; verify secrets drop/lock and no post-return writes.
