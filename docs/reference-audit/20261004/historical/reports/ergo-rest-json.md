## Confirmed findings

### REST-001 — Exact integral JSON number spellings are rejected

**P2; REPRODUCED; Scala-compatible inbound numbers.** `src/types.rs:92–121` claims circe BigInt acceptance but calls BigUint::parse_bytes on the serde number's decimal text. `mining.rs:191–193/216` uses this for b/d. Actual pinned JVM BigInt accepts bare100,1e2 and100.0 as100; Rust WorkMessage accepts100 but rejects1e2 (`1e+2`) and100.0. Arbitrary precision prevents floating-point loss but does not make textual decimal parsing equivalent. Canonical Scala emits plain integers, so ordinary canonical captures pass; valid exact alternate inbound spelling fails.

Parse JSON numbers into an exact integral decimal magnitude without f64, with bounded exponent/scale arithmetic and explicit unsigned policy. Preserve supported decimal strings, reject fractional/negative values according to the declared wire policy, and distinguish this policy from general signed circe BigInt. Acceptance: pinned comparisons for100/1e2/100.0, large exact values, zeros, nonintegral1.5, sign/string/exponent boundaries and b/d routes. No hash corruption or accepted invalid PoW was shown.

### REST-002 — Scala Long fields admit unsigned values beyond Long.MAX_VALUE

**P2; REPRODUCED; DTO domain and submit conversion.** `src/types.rs:191/212/243` declares box value and token amount asu64, while complete pinned JsonCodecs uses `.as[Long]` for asset amount95 and box/candidate value324/354. `decode.rs:180–221` forwards typed numbers into a trusted candidate constructor without checking the Scala signed maximum. Ordinary value9223372036854775808 is accepted by the Rust DTO and Submit output conversion; actual pinned JVM Long rejects it. This is observable wire-domain disagreement, even though downstream consensus amount/range checks may reject the transaction.

Enforce the intended nonnegative signed-Long JSON domain before canonical wire conversion, consistently for read and submit DTOs and token amounts. Separate numeric representability from consensus minimum/maximum supply rules. Acceptance: Long.MAX_VALUE−1/MAX/MAX+1, zero/negative, assets and all output entrypoints against pinned SDK decode; downstream rejection remains intact. No invalid-chain acceptance or overflow after validation was demonstrated.

### REST-003 — Aggregation loses individual constant-field boundaries

**P2; SOURCE_CONFIRMED; context/register field integrity.** `decode.rs:283–289/314–328` decodes each context value's hex but parses only after joining key/value bytes. `396–435` similarly joins all register bytes, then performs one aggregate parse/EOF check. Consequently a truncated field can borrow bytes belonging to a neighboring field, and an earlier field's suffix can become the next value/key. The aggregate can be valid while the separately described JSON values are invalid or different. This occurs before mode selection, so both modes inherit it.

A bounded source proof for two SBoolean fields: R4 hex010101 contains a complete true value0101 plus a suffix01; R5 hex01 is missing its boolean byte. Joining count02+010101+01 produces two complete0101 values with aggregate EOF. Parsing R5 with its own reader must fail. No operational payload or new malformed-input execution was performed. Pinned JsonCodecs deserializes each evaluated-value hex independently (`192–195`); scoped pinned ValueSerializer `396–422` creates a separate reader for each deserialize(bytes), so a field cannot borrow bytes from its neighbor. That reference helper does **not** assert field EOF: this finding proves lost field isolation, not that every trailing field byte violates the reference's acceptance policy.

Validate each constant with its own reader and explicit per-field framing policy before aggregation, preserving AST/raw provenance needed by each mode. Retain aggregate structure/EOF checks. Document whether trailing bytes are tolerated for exact SDK parity or rejected as a deliberate stricter boundary. Acceptance: separately truncated values fail despite valid concatenation; context keys/values cannot be shifted; ordinary bool/tuple/Concrete/GroupGenerator/provenance cases remain equivalent to the pinned independent field decoder.
