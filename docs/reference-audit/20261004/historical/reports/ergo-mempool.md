## Findings

### MP001 — Successful duplicate validation is not charged

**P2 · validation-cost accounting · SOURCE_CONFIRMED.** Every newly executed script validation must consume the applicable source budget even when the transaction already exists in the pool. In [admission/mod.rs:341](/home/arkadias/Coding/remote/ergo/ergo-mempool/src/admission/mod.rs:341), full validation runs before the duplicate branch at386–394. That branch returns immediately. Failed validation charges the accumulator at344–347; losers charge at439–441; other successes charge at461–464. Successful duplicates reach none of those charges.

`Mempool::process` and `Mempool::check` both use this decision path. The spend overlay intentionally retains pool-spent committed inputs for replacement, so an otherwise-valid pooled transaction can be successfully validated again. While budget headroom remains, repeated duplicate checks/submissions can execute scripts without moving the budget counters. This contradicts the documented check anti-DoS contract. The precheck still refuses if other work has already exhausted the budget; the finding does not claim that branch is bypassed.

Node's ordinary API Broadcast/CheckOnly calls process/check directly at [node/admission.rs:220](/home/arkadias/Coding/remote/ergo/ergo-node/src/node/admission.rs:220)/242, with PublicApi attribution on a public bind. Thus this is source-reachable from API input, including public submission when configured. Peer delivery has its own Accept/Ignore/Spam gate and ordinarily filters duplicate deliveries before admission; arbitrary peer replay is not asserted. Existing `duplicate_tx_rejected_idempotently` passes but asserts only Duplicate and unchanged pool size, not validation calls or cost. Source-only proof and independent root source challenge establish the control flow; **no custom workload, denial-of-service measurement, Scala comparison or full-transaction experiment was executed**.

Charge the actual executed cost before any post-validation return, retaining the DemotedFromBlock exemption, or safely reject a known duplicate before expensive validation under a clear corrected-proof/context contract. Acceptance should extend ordinary duplicate/check tests to pin cost conservation and eventual precheck exhaustion without pool or relay mutation. Keep validation failure and successful duplicate distinct from free cheap gates.

### MP002 — Admission and reorg lose the remaining descendant frontier

**P2 · bounded dependency removal · SOURCE_CONFIRMED.** [pool.rs:388](/home/arkadias/Coding/remote/ergo/ergo-mempool/src/pool.rs:388) bounds the number of removed nodes and returns unvisited descendants as a frontier. The debit wrapper at590–598 discards the frontier; the explicit frontier wrapper preserves it. Single admission replacement/capacity at [admission/mod.rs:732](/home/arkadias/Coding/remote/ergo/ergo-mempool/src/admission/mod.rs:732)/787, package conflict/capacity at mempool1094/1177, and applied input-conflict eviction at [reorg.rs:117](/home/arkadias/Coding/remote/ergo/ergo-mempool/src/reorg.rs:117) use the discarding wrapper. They do not enqueue follow-up orphan removal.

When a removed family exceeds max_family_depth (default500 nodes, configurable smaller), remaining children spend outputs of parents that are no longer pooled and were not confirmed. Reverse index cleanup removes the stale parent edge, so internal map/index checks can still pass while those children remain unmineable and retain pool bytes/outputs. Recheck deliberately keeps UnresolvedInput as a potentially transient reorg dependency, so it cannot repair this particular orphan solely by validation. Descendants whose inputs resolve through another still-retained orphan may also survive recheck. Capacity/weight eviction may eventually remove them, but no guaranteed frontier continuation remains. Mining independently revalidates its candidate; this is not an accepted invalid block claim.

The **existing executed** `remove_with_descendants_respects_max_depth`/frontier tests prove cap2 leaves nodes3/4 and that explicitly carrying the frontier finishes removal. The existing hard-invalid recheck test exercises the correct follow-up drain with max_family_depth2. Production caller omission is source-confirmed, not a newly executed custom wide/deep or fork scenario. Fix every committed descendant-removal caller to carry a bounded frontier into coherent follow-up cleanup/revocation, or use an equivalent explicitly bounded structural invalidity queue. Preserve confirmation's intentional no-cascade semantics. Acceptance should apply the existing cap fixture through ordinary replacement, capacity, package and applied-conflict paths and assert all eventual removals/actions plus unrelated sibling survival.

### MP003 — An admitted package reports the child as rejected

**P2 · public admission outcome · SOURCE_CONFIRMED.** With staging enabled, child single-tx validation initially reports UnresolvedInput when its held parent is outside the live pool. At [mempool.rs:372](/home/arkadias/Coding/remote/ergo/ergo-mempool/src/mempool.rs:372), `try_package` can then validate and atomically admit the parent/child package. It removes staging suppression, emits every member's BroadcastInv/Admitted event, and calls on_admitted at809–866. However, process only appends those actions and returns its immutable **initial rejected outcome** at399.

Node Broadcast matches that Rejected into SubmitError, then unconditionally routes/flushed actions before returning Err at [node/admission.rs:194](/home/arkadias/Coding/remote/ergo/ergo-node/src/node/admission.rs:194)–271. Consequently a successful opt-in package can enter and be advertised while its submission reports failure; peer counters likewise count rejection although the child was inserted. This mismatch can cause unnecessary retries and makes callers/telemetry unable to trust the API outcome. It requires `staging_enabled=true`; default false avoids the path. No rollback of the successful package is desired.

Existing package threshold/RBF tests actually execute insertion and announcement but bind the child's outcome as `_co`; they leave this assertion gap. Root independently corroborated the exact Mempool/Node path. **No new custom demonstration or HTTP request was executed.** Return a structured package result carrying the admitted child's ID/fee/size and update process's final outcome only after successful commit. Keep held/rejected packages and check-only semantics distinct. Acceptance is the existing ordinary package-success fixture asserting Admitted alongside both IDs/actions, with Node submission mapping and rejection controls preserving current no-mutation behavior.

### MP004 — Package revalidation skips the remaining source budget gates

**P2 · package budget enforcement · SOURCE_CONFIRMED.** [validate_package_child](/home/arkadias/Coding/remote/ergo/ergo-mempool/src/mempool.rs:955) constructs a per-tx cost cap, evaluates, then charges the accumulator on pass/fail. It never calls `pre_admission_check`. `try_package` invokes it for every stale held ancestor at729 and the child at772. The one outer initial check applies only to the arriving child's source before those extra evaluations; an ancestor can have a different already-exhausted peer/source budget. The aggregate package-cost cap is checked at1052 **after all validations**, so it controls seating rather than stopping excess evaluation.

Thus an opt-in package can continue validating members after the shared/local/per-peer budget becomes exhausted, including members whose own source was already exhausted at package start. Costs are **charged**, not hidden; member count and individual max_tx_cost remain finite bounds (default at most24 members), but configured block/source allowances and the expected one in-flight overshoot are not enforced per evaluation. Same-tip cached parent facts require no new scripts and are not the problem. Demoted re-admission retains its deliberate exemption. No workload, timing or large-package demonstration was run.

Gate each newly executed member under its actual source and maintain an incremental work budget before proceeding; defer safely when exhausted rather than reclassifying a local budget refusal as consensus-invalid or silently deleting a held ancestor. Account failed validation too, and keep the final aggregate policy cap. Acceptance should extend ordinary stale-held and same-height-reorg tests with a near/exhausted source budget, verify no additional validator call occurs after exhaustion, preserve bounded deferred staging and test DemotedFromBlock separately. Current tests cover package cost rejection and tip freshness but not per-member remaining-budget enforcement.

### MP005 — Invalidation FIFO can grow beyond the configured cache cap

**P2 · cache allocation / eviction · SOURCE_CONFIRMED.** [InvalidationCache::insert](/home/arkadias/Coding/remote/ergo/ergo-mempool/src/invalidation.rs:103) overwrites `entries[tx_id]` but **always appends** `(tx_id, now)` to `by_insertion`. Capacity only consults the map's number of distinct IDs, so repeated insertion of one ID grows the FIFO independently of max_size until its four-hour TTL expires. Prune protects refreshed entries by checking insertion timestamps; capacity eviction at107–110 does not. Popping a stale tuple can therefore delete a newer live map entry and fail to evict the oldest current record; stale tuples referencing absent IDs can also fail to free capacity.

This is reachable through current admission, not merely a raw cache API: canonical-ID invalidation deliberately filters Inv fetching but does not block direct submission, and each cached validation failure re-inserts via record_failed_tx. The real validator's reemission-output policy refusal occurs before script cost; its existing ordinary test submits the same bytes twice, confirms zero cost, no peer penalty, and cached ID both times. Consequently this path can refresh the same map ID without consuming script budget while accumulating queue records. HTTP/delivery bounds still exist; **unlimited allocation rate, memory exhaustion and operational denial of service were not measured or demonstrated**. The source-confirmed defect is that the stated entry cap does not bound bookkeeping memory and stale eviction lacks the freshness guard.

Maintain at most one current queue/list record per ID, or independently cap and compact stale records while checking their generation/timestamp before map removal. Preserve direct corrected-proof acceptance and fetch-filter semantics. Acceptance should extend existing reinsertion/cap/TTL unit tests to bound both structures, exercise refreshed-ID eviction and ensure distinct insertions never exceed the configured capacity (including a defined zero-cap policy). Current reinsertion test only checks map len1 and reason replacement.
